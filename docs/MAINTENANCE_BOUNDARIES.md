# Maintenance boundaries

This document defines which repository areas are supported, which are retained
for reproducibility, and which files must stay outside version control. It is
the safety boundary for structural cleanup: moving code or reducing duplication
must not silently expand the scientific claims of a historical workflow.

## Repository categories

Every file belongs to one of the following categories.

| Category | Maintenance promise | Expected location |
| --- | --- | --- |
| Supported workflow | Tested, linted, documented, and safe for new controlled work | `eoslab.py`, `configs/`, selected `framework/` and `src/` modules |
| Maintained research utility | Kept working when it supports an active audit, but not a primary public interface | `framework/audit_*.py`, selected reporting utilities |
| Frozen compatibility workflow | Retained to reproduce historical thesis work; no new features and no claim of current safeguards | root legacy launchers and historical Streamlit applications |
| Locked scientific evidence | Intentionally versioned, compact, provenance-bearing results that must not be regenerated in place | `docs/` today; a dedicated evidence tree after artifact migration |
| Test fixture | Small deterministic input or expected result used only by automated tests | `tests/fixtures/` |
| Reproducible generated output | Regenerated by a documented command and never reviewed as source | ignored `runs/`, `outputs/`, plots, temporary tables, and model artifacts |
| Personal scratch material | Not part of the repository contract | untracked notebooks, `tmp/`, editor checkpoints, and local logs |

## Supported post-thesis surface

The supported entry point is `eoslab.py`. Its maintained implementation surface
currently includes:

- `framework/eos_catalog.py` and `framework/eos_sweep.py`;
- `src/eoslab_runtime.py`, `src/experiment_config.py`, and
  `src/family_workflow.py`;
- the controlled generation, sequence solving, experiment runner, experiment
  reporting, and run-logging modules used by the launcher;
- the family modules imported by the audited family workflow; and
- the regression suite under `tests/`.

Supported code must pass the repository's readiness check, regression suite,
and maintained-code lint command. New controlled work must enter through
`eoslab.py`; a historical launcher must not write into a managed run directory.

## Maintained research utilities

Audit scripts in `framework/` are maintained when they produce or validate a
documented evidence record. They may expose a narrower command-line interface
than `eoslab.py`, but they must declare their inputs, outputs, and scientific
interpretation boundary in the corresponding document.

An audit script is not automatically part of the supported public interface.
Promotion to the supported surface requires regression tests and inclusion in
the maintained-code lint scope.

## Frozen compatibility surface

The following entry points are historical compatibility workflows:

- `physics_main.py`, `main.py`, and `perturb_main.py`;
- the root `family_*.py` scripts;
- `app_ref.py` and `perturb_app_ref.py`; and
- exploratory notebooks and notebook checkpoints.

Frozen compatibility code may receive a narrowly scoped fix when it cannot
perform its documented reproduction role. It should not receive new features,
be used as the foundation for a new workflow, or be presented as sharing every
safeguard of the supported launcher.

Before compatibility files are moved, their original command and artifact
layout must be documented. A temporary wrapper should preserve a command that
is still referenced by documentation or an evidence record.

## Artifact policy

Ignored paths are not a suitable permanent home for versioned evidence. Before
removing an already tracked artifact, classify it as one of the following:

1. Reproducible output: remove it from the Git index and document the command
   that recreates it.
2. Test fixture: reduce it to the smallest deterministic sample and move it to
   `tests/fixtures/`.
3. Locked evidence: move a compact result, its configuration, provenance, and
   integrity hash to a clearly named evidence location.
4. Large source dataset: record its origin and integrity hash, then store it in
   an appropriate external artifact system rather than ordinary Git.
5. Obsolete artifact: remove it only after confirming that no test, document,
   configuration, or workflow references it.

Generated commands must use ignored, non-overwriting directories. Tests must
write to pytest temporary directories and must not mutate tracked artifacts.

## Change discipline

Each cohesive cleanup follows this lifecycle:

1. Branch from the current remote default branch.
2. Make one reviewable structural or policy change.
3. Run the relevant local checks and inspect the complete diff.
4. Commit only explicitly scoped files.
5. Push and open a pull request with the motivation and validation results.
6. Let CI and review complete before merging.
7. Synchronize the default branch before creating the next cleanup branch.

Do not combine numerical-parameter changes with file moves, broad formatting,
or dependency migrations. Compatibility facades should be introduced before
public imports move, and removed only after their callers and documentation are
updated.

## Required validation gates

The minimum supported-code gate is:

```powershell
py -3 eoslab.py doctor
py -3 -m pytest -q
py -3 -m ruff check eoslab.py framework src tests *.py
```

Structural changes to scientific routines also require focused equivalence
tests for the affected numerical outputs. Configuration refactors must preserve
canonical hashes unless a schema version is deliberately changed. Runner and
reporting refactors must preserve terminal states, manifest semantics, and
artifact schemas.

## Cleanup completion criteria

The staged cleanup is complete when:

- the supported entry point and implementation surface are immediately clear;
- all maintained Python code is linted in CI;
- the regression suite passes from a clean checkout on every supported Python
  and operating-system combination;
- routine experiments and tests leave `git status` clean;
- generated output, locked evidence, and test fixtures have distinct homes;
- large modules are divided by responsibility while preserving their public
  interfaces; and
- installation and execution no longer rely on an accidental working
  directory.
